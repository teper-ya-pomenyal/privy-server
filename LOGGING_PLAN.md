# План улучшения логирования бэкенда

Контекст: аудит на 29.09.2026. Сервисы: gateway, user_service, catalog_service,
streaming_service (+ jwtmanager — библиотека без транспорта). Согласован с
`ADMIN_BACKEND_PLAN.md` (его Фаза 6 «Логи» становится здесь Фазой 4 и
переиспользует её решения).

---

## Текущее состояние (по аудиту)

Факты, на которых строится план:

1. **Библиотек логирования нет.** Только stdlib `log` без инициализации
   (дефолтный логгер → stderr, только дата+время). ~57 вызовов на 4 сервиса,
   jwtmanager молчит. Один `fmt.Printf` (баннер streaming_service, без
   таймстемпа).
2. **Уровней нет вообще.** Ни типа уровня, ни фильтрации. `log.Fatal` —
   де-факто «стартовая ошибка»; всё остальное — один неразличимый поток.
3. **Формат — plain text, неструктурированный.** HTTP-доступ-лог пишется
   chi-`middleware.Logger` в stdout в своём формате; остальное — в stderr.
   Два потока на сервис.
4. **Request ID нет.** `middleware.RequestID` нигде не зарегистрирован, `X-Request-Id`
   не встречается, gRPC-вызовы идут с голым ctx (никакой metadata). user_id
   лежит в контексте gateway, но не логируется и не пробрасывается в сервисы.
   Один пользовательский действие = несвязываемые строки в логах 2–3 сервисов.
5. **Дубль access-лога для /stream:** `gateway/cmd/main.go:61` монтирует
   streamingRouter в родительский роутер, у обоих зарегистрирован
   `middleware.Logger` → каждый запрос /stream даёт две строки.
6. **gRPC-интерцепторы скопипащены** байт-в-байт между user_service и
   catalog_service (`internal/delivery/grpc/interceptors.go`); строка panic-
   recovery не содержит метода (`log.Println(err, r)`). Клиентских
   интерцепторов нет ни у кого.
7. **streaming_service:** 7 голых `log.Println(err)` в
   `internal/delivery/http/stream.go` — без track id, метода, причины.
8. **`log.Fatal` вне main:** конструктор роутера
   (`gateway/internal/handlers/streaming_router.go:18`) и геттеры конфигов
   (`config.go` у трёх сервисов) убивают процесс вместо возврата ошибки.
9. **Ошибки не логируются на границе gateway:** провал gRPC-вызова виден одной
   строкой в целевом сервисе; gateway пишет только статус 4xx/5xx в access-лог.
   Конвенция ошибок (sentinels + `mapDomainError`, без `%w`-обёрток —
   `AGENTS.md:74-84`) рабочая и не меняется.
10. **Вывод не настроен:** stdout/stderr, без ротации. У `docker-compose.yml`
    нет секции `logging:` → Docker json-file без ограничений.
11. **Разнобой:** сообщения RU/EN вперемешку (и опечатка «остановлени»),
    разные стили Fatal/Fatalf/Fatalln, `log.Println(pong)` («PONG» при старте
    Redis), банер listening есть у 2 из 4 сервисов.
12. **Чувствительные данные:** прямых утечек нет (пароли/токены/JWT не
    печатаются). Риск-паттерн: геттеры конфига печатают значение переменной
    при ошибке парсинга — безопасно для int/duration, но опасно как шаблон.

## Целевая картина

- **slog** (stdlib, Go 1.26 уже в go.mod) — JSON в **stdout**, уровень из env
  `LOG_LEVEL` (default `info`). Без новых зависимостей: производительность
  стриминга от логгера не зависит, zap/zerolog не обоснованы.
- **Один общий модуль `logging/`** (по образцу `jwtmanager`): инициализация
  логгера, chi-мидлвари (request id + access-лог), gRPC-сервер/клиент
  интерцепторы, проброс `x-request-id` через metadata. Убивает копипасту
  интерцепторов и не плодит 4 копии мидлварей.
- **Request id сквозной:** генерация/приём `X-Request-Id` в gateway →
  metadata `x-request-id` → user/catalog/streaming сервисы. Каждый лог-запрос
  несёт `request_id`, access-лог дополнительно `user_id`.
- **Уровни:** `debug` — разработка; `info` — lifecycle и access-лог;
  `warn` — деградации (redis недоступен → rate-limit off) и 4xx;
  `error` — 5xx и неожиданные ошибки; `fatal` — только в `main()`.
- **Правило одного места:** ошибка логируется один раз — на границе
  (handler/интерцептор) с контекстом (request_id, метод, идентификаторы
  сущности). Внутренние слои по-прежнему возвращают sentinel-ошибки без
  логирования.
- **Сообщения на английском**, один стиль, одинаковый баннер listening у всех
  сервисов.

## Фаза 1 — Переход на slog (фундамент, механика)

Самая дешёвая и дающая больше всего. ~1 день.

1. Новый модуль `logging` (🔒 общий, как jwtmanager):
   `logging.New(service string) *slog.Logger` — JSONHandler → stdout, уровень
   из `LOG_LEVEL` (default `info`), атрибуты `service=<name>`, `version` при
   необходимости. Для локальной разработки — `LOG_FORMAT=text`.
2. В каждом `cmd/main.go`: инициализировать логгер, заменить все `log.*` /
   `fmt.Printf` на slog с корректными уровнями:
   - старт/баннер listening — `info` (унифицировать строку, добавить её в
     user_service и catalog_service, где её нет);
   - graceful shutdown — `info`; таймаут шатдауна — `warn`;
   - «redis unavailable, rate limit disabled» (gateway main.go:50) — `warn`;
   - ошибки запуска — `error` + один `Fatal` в main.
3. Убрать `log.Fatal` из не-main кода (🔒 меняет сигнатуры):
   - `streaming_router.go:18`: `NewStreamingRouter` возвращает
     `(*chi.Mux, error)`; main обрабатывает;
   - геттеры конфигов (`gateway/user/catalog config.go`): вместо Fatal —
     возврат ошибки, main решает. Заодно не печатать значение переменной в
     сообщении об ошибке парсинга (паттерн-гигиена, п.12 аудита).
4. Заменить точечные вызовы в handler'ах (gateway catalog_handlers.go — 7
   Printf, streaming stream.go — 8) на slog с уровнями: отказы unsafe-path —
   `warn`, ошибки cleanup/rate-limiter — `warn`/`error`.
5. Удалить `log.Println(pong)` (redis_session_store.go:38); при желании —
   `debug`-строка «redis ping ok».
6. Сообщения: перевести русские строки на английский, убрать опечатки
   («остановлени»), единый стиль.
7. `docker-compose.yml`: добавить каждому сервису
   `logging: {driver: json-file, options: {max-size: "10m", max-file: "3"}}`.

**Готовность:** все сервисы пишут JSON в stdout с уровнями; `LOG_LEVEL=debug`
показывает debug-строки; kill сервиса из-за ошибки конфига происходит только
в main.

## Фаза 2 — Request ID и access-лог

Связываемость запросов между сервисами. ~1–1.5 дня.

1. 🔒 В модуле `logging`:
   - chi-мидлварь RequestID: принимать входящий `X-Request-Id` или
     генерировать `uuid`; класть в ctx + заголовок ответа;
   - chi-мидлварь access-лога на slog (замена chi `middleware.Logger`):
     `request_id, method, path, status, duration, bytes, remote_ip, user_id,
     err` — неаутентифицированные запросы без `user_id`;
   - gRPC-сервер-интерцепторы: recovery (с методом в строке panic!) и
     logging (method, duration, code, request_id) — взамен двух копий
     `interceptors.go`;
   - gRPC-клиент-интерцептор: прокидывает `x-request-id` из ctx в metadata
     (навесить на все конны в gateway и streaming_service).
2. Серверные интерцепторы читают `x-request-id` из metadata в ctx, логгер
   берёт его из ctx автоматически.
3. `user_id` в access-логе: паттерн — мидлварь RequestID кладёт в ctx
   изменяемый `*RequestLogFields`; auth-мидлварь
   (`gateway/internal/middlewares/auth.go`) дописывает туда `user_id`;
   access-мидлварь читает после `next.ServeHTTP`. (Контекст-значения от
   внутреннего auth наружу не видны — поэтому holder, а не ctx.)
4. Починить дубль access-лога /stream: снять регистрацию Logger/Recoverer
   либо в streaming_router.go:32-33, либо в месте mount (main.go:59-61).

**Готовность:** один и тот же request_id виден в gateway, user/catalog
service и streaming_service; grep по request_id показывает весь путь запроса;
/stream даёт одну access-строку.

## Фаза 3 — Дисциплина ошибок на границах

Маленькая, но решает «почему 500». ~0.5 дня.

1. streaming_service `stream.go`: каждый отказ — `slog.Error("stream failed",
   "track_id", id, "request_id", …, "err", err)` вместо голого
   `log.Println(err)`. http.Error остаётся как есть.
2. Gateway: при ошибке gRPC-вызова логировать `warn`/`error` с методом,
   request_id, gRPC-кодом и итоговым HTTP-статусом (сегодня gateway не пишет
   ничего, п.9 аудита). Место — единый хелпер рядом с `mapGRPCError`
   (`error_maping.go`).
3. Правило уровней: 4xx — `warn`, 5xx — `error` (в access-логе и в
   gRPC-интерцепторе по коду).
4. Зафиксировать конвенцию в `AGENTS.md`/`CLAUDE.md`: новый раздел
   «Логирование» (slog, уровни, английский, request_id, «логируем на
   границе один раз», никакого паролей/токенов/JWT в логах). Заодно
   поправить устаревшее описание `internal/middlewares` (AGENTS.md:37 —
   там только auth, см. аудит).

**Готовность:** у любого 5xx есть строка с request_id, сервисом и причиной;
в логах нет дублей одной ошибки.

## Фаза 4 — Логи для админки (= Фаза 6 ADMIN_BACKEND_PLAN)

Когда ROLE OWNER из Фазы 0 админ-плана готова. Оценка после выбора схемы.

1. 🔒 В модуле `logging`: Handler-обёртка «ring buffer» — последние N
   (например, 1000) записей в памяти на процесс, tee в stdout.
2. `GET /admin/logs` (последние N, фильтры по уровню/сервису, поллинг; без
   SSE) — за `RequireOwner`. Для gateway — прямой роут; для user/catalog —
   поверх gRPC или отдельный HTTP-порт на сервисе (решить при реализации;
   второй вариант проще, у сервисов HTTP сейчас нет).
3. Фронт админки: вкладка «Логи» — мердж с уже существующим HTTP-журналом.
4. Кросс-процессная агрегация (Loki / Redis Streams) и SSE — отдельное
   инфраструктурное решение, **не** в этом плане (как и в админ-плане).

**Готовность:** владелец видит последние логи всех сервисов в админке без
доступа к Docker.

## Фаза 5 — Гигиена (по мере возможности)

1. Тихий тест на «в логах нет секретов»: юнит-тест на сериализацию
   login/refresh ответов и конфига — в выводе логгера не встречаются
   access/refresh token и пароль.
2. Метрики на базе логов не строим; если позже понадобится Grafana —
   JSON-from-stdout уже совместим с Loki/promtail без правок кода.
3. `slog`-атрибут `version`/`commit` в стартовой строке сервисов (когда
   появится CI-сборка).

## Открытые вопросы

1. Общий модуль `logging` vs копия в каждом сервисе: план предполагает модуль
   (интерцепторы уже дублируются, мидлвари добавили бы ещё 2 копии). Если
   модуль не хочется — Фаза 2 дорожает на дублирование, но реализуема.
2. `GET /admin/logs` для user/catalog: gRPC-метод vs отдельный HTTP-порт на
   сервисе — решить при реализации Фазы 4.
3. Нужно ли логировать исходящие gRPC-вызовы gateway'я отдельной строкой
   (клиент-интерцептор с логом, не только пробросом id) — дублирует
   серверный интерцептор, по умолчанию выключено.

## Чего этот план сознательно не делает

- Не меняет конвенцию ошибок (sentinels + `mapDomainError`, без `%w`) —
  она рабочая и зафиксирована в AGENTS.md.
- Не вводит zap/zerolog/logrus — без обоснованной потребности в
  производительности.
- Не поднимает Loki/Grafana/ELK — инфраструктурное решение отдельно
  (совпадает с позицией ADMIN_BACKEND_PLAN, Фаза 6).
- Не пишет логи в файлы из сервисов — stdout + ротация Docker (12-factor).
